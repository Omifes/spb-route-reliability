# Реализация этапов 1–4

Документ описывает текущее состояние проекта: мок-агрегатор транспортных API
(этап 1), бизнес-логику и REST API (этап 2), слой данных PostgreSQL (этап 3),
а также инфраструктурную часть этапа 4 — логирование в STDOUT и CI.
Frontend в текущую реализацию пока не входит.

## Статус этапов

| Этап | Содержание | Статус |
|---|---|---|
| 1 | Агрегатор и интеграция с транспортными API (мок-источник) | реализован |
| 2 | Бизнес-логика и REST API | реализован |
| 3 | Слой данных PostgreSQL | реализован |
| 4 | Логирование, CI и frontend | частично: логирование и CI готовы, frontend нет |

## Архитектура

```text
Клиент (curl, Postman, будущий frontend)
        │
        │ HTTP Basic Auth, JSON
        ▼
Spring Boot backend
  web/          REST-контроллеры, DTO, ошибки, логирование запросов
  service/      бизнес-логика
  reliability/  расчёт риска
  security/     Basic Auth, демо-пользователь
  config/       Security, CORS
  integration/  агрегатор и мок-источник
  repository/   Spring Data JPA
  domain/       JPA-сущности
        │
        │ JDBC / Hibernate
        ▼
PostgreSQL 16
```

Ключевые принципы:

- схему БД создаёт только Flyway, Hibernate проверяет соответствие сущностей;
- API работает с внешними идентификаторами маршрутов и остановок;
- пользователь имеет доступ только к своим поездкам;
- при недостатке данных сервис сообщает об ограничении, а не подставляет
  вымышленный прогноз.

# Этап 3. Слой данных PostgreSQL

## Что сделано

- Настроены PostgreSQL 16, Flyway и Spring Data JPA.
- Созданы две миграции: `V1__init_schema.sql` и `V2__create_indexes.sql`.
- Реализованы 7 JPA-сущностей и 7 репозиториев.
- Добавлены ограничения целостности и индексы под основные запросы.
- Интеграционные тесты используют встроенный PostgreSQL, Docker не требуется.

## Таблицы

| Таблица | Назначение |
|---|---|
| `users` | Пользователи сервиса, e-mail и BCrypt-хеш пароля |
| `routes` | Маршруты общественного транспорта |
| `stops` | Остановочные пункты |
| `route_stops` | Упорядоченные остановки маршрута по направлениям |
| `saved_trips` | Сохранённые поездки пользователей |
| `historical_statistics` | Суточные агрегаты задержек и отмен |
| `transport_updates` | Сырые события внешнего агрегатора |

Служебная таблица `flyway_schema_history` создаётся Flyway автоматически.

## Схема и ограничения

Основные решения:

- `BIGSERIAL` для первичных ключей;
- `TIMESTAMPTZ` для моментов времени, `TIME` для локального времени прибытия;
- `NUMERIC(9, 6)` для координат с проверкой допустимого диапазона;
- `JSONB` для исходного payload внешнего API;
- `direction_id` соответствует GTFS: `0` или `1`;
- внешние ID маршрутов и остановок уникальны.

Значимые ограничения:

| Ограничение | Смысл |
|---|---|
| `ux_users_email_lower` | e-mail уникален без учёта регистра |
| `ux_routes_external_id` | уникальность внешнего ID маршрута |
| `ux_stops_external_id` | уникальность внешнего ID остановки |
| `ck_saved_trips_different_stops` | остановки отправления и назначения различаются |
| `ux_historical_statistics_route_stop_date` | одна запись статистики на маршрут, остановку и дату |
| `ck_historical_status_sum` | опоздавшие + отменённые не больше общего числа поездок |
| `ck_transport_updates_status` | статус только `ON_TIME`, `DELAYED`, `CANCELLED`, `UNKNOWN` |
| `ck_transport_updates_delay` | задержка в допустимом диапазоне |

`transport_updates` намеренно не имеет внешних ключей: это staging-таблица
сырых событий. Маршрут и остановка хранятся как внешние ID и могут появиться в
справочниках позже самого события.

## Индексы

| Индекс | Назначение |
|---|---|
| `ix_stops_name_trgm` | поиск остановок по части названия через `ILIKE` |
| `ix_saved_trips_user_created` | список поездок пользователя по дате |
| `ix_historical_statistics_route_date` | статистика маршрута за период |
| `ix_historical_statistics_stop_date` | статистика остановки за период |
| `ix_historical_statistics_stat_date_brin` | диапазонные запросы по датам |
| `ix_transport_updates_route_observed` | последнее событие по маршруту |
| `ix_transport_updates_stop_observed` | последнее событие по остановке |
| `ix_transport_updates_observed_brin` | очистка и анализ по времени |

## JPA-слой

Сущности находятся в `backend/src/main/java/ru/spb/transit/domain`, репозитории —
в `backend/src/main/java/ru/spb/transit/repository`.

Репозитории содержат запросы для:

- поиска маршрута и остановки по внешнему ID;
- списка поездок пользователя;
- поиска поездки по ID и владельцу;
- последнего события по маршруту и остановке;
- статистики по маршруту и остановке за диапазон дат;
- удаления устаревших транспортных событий.

## Как проверяется схема

При старте приложения:

1. Flyway проверяет и применяет миграции.
2. Hibernate работает с `ddl-auto=validate` и только проверяет схему.
3. `clean-disabled=true` запрещает случайную очистку базы.

Тесты поднимают встроенный PostgreSQL 16.15 и прогоняют миграции на реальной
СУБД, поэтому `JSONB`, `pg_trgm` и BRIN-индексы проверяются так же, как в
production.

# Этап 2. Бизнес-логика и REST API

## Что сделано

- Basic Auth по таблице `users` с BCrypt.
- Демо-пользователь для локального запуска.
- CRUD сохранённых поездок с проверкой владельца.
- Расчёт текущего статуса поездки.
- Расчёт надёжности маршрута по исторической статистике.
- Валидация входных данных и единый формат ошибок.
- CORS для frontend, обслуживаемого с другого origin.
- 38 unit- и интеграционных тестов.

## Аутентификация и доступ

Все методы `/api/**` требуют HTTP Basic Auth.

```http
Authorization: Basic ZGVtb0BzcGIubG9jYWw6ZGVtbw==
```

1. `AppUserDetailsService` ищет пользователя по e-mail.
2. Пароль проверяется через BCrypt.
3. При отсутствии или неверных данных возвращается `401 Unauthorized`.
4. Сессия не создаётся: каждый запрос содержит учётные данные.

Демо-пользователь:

| Поле | Значение |
|---|---|
| E-mail | `demo@spb.local` |
| Пароль | `demo` |

В production демо-пользователь отключается через
`APP_DEMO_USER_ENABLED=false`.

Поездка доступна только владельцу. Чужая поездка возвращает `404 Not Found`,
чтобы не раскрывать факт её существования.

## REST API

| Метод | Endpoint | Назначение | Ответ |
|---|---|---|---|
| `GET` | `/api/trips` | Поездки текущего пользователя | `200 OK` |
| `POST` | `/api/trips` | Создание поездки | `201 Created` |
| `GET` | `/api/trips/{id}/status` | Статус и прогноз прибытия | `200 OK` |
| `GET` | `/api/trips/{id}/reliability` | Оценка надёжности | `200 OK` |
| `DELETE` | `/api/trips/{id}` | Удаление поездки | `204 No Content` |

API использует внешние идентификаторы:

- `routeId` — `routes.external_id`;
- `fromStopId`, `toStopId` — `stops.external_id`.

Внутренние первичные ключи БД наружу не передаются, кроме `id` сохранённой
поездки.

## Создание и хранение поездки

`TripService` выполняет следующие проверки:

1. Название не пустое и не длиннее 255 символов.
2. Маршрут существует.
3. Остановка отправления существует.
4. Остановка назначения существует.
5. Остановки различаются.
6. Время прибытия передано в формате `HH:mm`.

При создании сохраняется `direction_id = 0`, так как контракт API не передаёт
направление движения.

## Статус поездки

`TripStatusService` определяет, где сейчас транспорт, когда он будет на нужной
остановке и успеет ли пользователь.

### Выбор источника данных

1. Сначала ищется последнее обновление по маршруту и остановке назначения.
2. Если его нет — последнее обновление по маршруту.
3. Если обновлений нет — `dataStatus = "unavailable"`.

### Актуальность данных

| `dataStatus` | Условие |
|---|---|
| `current` | возраст данных не больше `STATUS_CURRENT_WINDOW` (по умолчанию 5 минут) |
| `stale` | возраст больше 5 минут, но не больше `STATUS_STALE_WINDOW` (по умолчанию 60 минут) |
| `unavailable` | данных нет или они старше 60 минут |

При `unavailable` поля `etaMinutes`, `arrivalTime`, `delayMinutes` и
`willArriveOnTime` равны `null`. Сервис не подставляет фиктивные значения.

### Расчёт прибытия

1. Если известно `actual_at`, используется оно.
2. Иначе используется `scheduled_at + delay_seconds`.
3. Если нет ни того, ни другого, прогноз не строится.

На основе прогноза:

- `etaMinutes` — минуты до прибытия, не меньше нуля;
- `arrivalTime` — время прибытия в `Europe/Moscow` в формате `HH:mm`;
- `delayMinutes` — задержка из `delay_seconds` или разница `actual_at` и
  `scheduled_at`;
- `willArriveOnTime` — `true`, если прибытие не позже требуемого времени.

Особые случаи:

- отменённый рейс: прогноза прибытия нет, `willArriveOnTime = false`;
- прогноз невозможен: `willArriveOnTime = null`;
- `nextStop` — следующая остановка после текущей позиции; если определить
  нельзя, возвращается остановка назначения поездки;
- `dataUpdatedAt` — время последнего использованного обновления.

## Оценка надёжности

`ReliabilityService` оценивает маршрут по историческим суточным агрегатам.

Параметры:

- `periodDays` по умолчанию `30`;
- допустимый диапазон — от `1` до `365`;
- статистика берётся по маршруту и остановке назначения;
- учитываются только дни внутри периода.

Почему остановка назначения, а не весь маршрут: иначе одни и те же рейсы
посчитались бы на каждой остановке маршрута несколько раз.

### Формулы

```text
trips      = Σ trips_count
delayed    = Σ delayed_trips
cancelled  = Σ cancelled_trips

averageDelay = Σ(average_delay_i × trips_count_i) / Σ trips_count_i

delayedTripsPercent   = delayed / trips × 100
cancelledTripsPercent = cancelled / trips × 100
```

Средняя задержка взвешивается по числу поездок, поэтому дни с большим числом
рейсов влияют сильнее. Проценты округляются до двух знаков.

### Достаточность данных

Оценка считается достоверной, если:

- набрано не менее 10 поездок;
- известна средняя задержка.

Иначе:

```json
{
  "riskLevel": "unknown",
  "dataSufficient": false
}
```

### Уровни риска

| Уровень | Правило |
|---|---|
| `high` | средняя задержка ≥ 8 мин, или опоздания ≥ 25 %, или отмены ≥ 5 % |
| `medium` | средняя задержка ≥ 4 мин, или опоздания ≥ 12 % |
| `low` | остальные случаи при достаточных данных |
| `unknown` | данных недостаточно |

Пороги заданы константами в `ReliabilityCalculator` и могут быть уточнены
после анализа реальной статистики.

## Валидация и ошибки

Проверки выполняются на трёх уровнях:

1. Bean Validation — обязательные поля, длина, формат `HH:mm`.
2. Бизнес-проверки — существование маршрута и остановок, разные остановки,
   корректный период, принадлежность поездки.
3. Ограничения PostgreSQL — защита целостности на уровне БД.

Единый формат ошибки:

```json
{
  "timestamp": "2026-11-18T10:00:00Z",
  "status": 400,
  "error": "Bad Request",
  "message": "Некорректные данные запроса",
  "path": "/api/trips",
  "fieldErrors": {
    "requiredArrivalTime": "Требуемое время прибытия обязательно"
  }
}
```

| Код | Когда возвращается |
|---|---|
| `400` | неверный JSON, ошибка валидации, неизвестный маршрут или остановка |
| `401` | нет или неверные учётные данные |
| `404` | поездка не найдена или принадлежит другому пользователю |
| `500` | непредвиденная ошибка сервера |

## CORS

Если frontend открыт с другого origin, сервер разрешает preflight `OPTIONS`
без аутентификации и возвращает заголовки CORS.

- разрешённые методы: `GET`, `POST`, `DELETE`, `OPTIONS`;
- разрешённые заголовки: `Authorization`, `Content-Type`;
- список origin задаётся через `APP_CORS_ALLOWED_ORIGINS`.

По умолчанию разрешены локальные адреса `localhost:5500`, `127.0.0.1:5500`,
`localhost:8000`, `localhost:3000`, `localhost:5173`.

# Сквозной сценарий

1. Пользователь проходит Basic Auth.
2. Создаёт поездку: маршрут, остановки, требуемое время.
3. Запрашивает `/status`:
   - сервис находит последнее событие по остановке назначения;
   - проверяет свежесть данных;
   - рассчитывает прибытие и `willArriveOnTime`.
4. Запрашивает `/reliability`:
   - сервис читает суточную статистику за период;
   - считает среднюю задержку и проценты;
   - определяет риск или сообщает о недостатке данных.
5. Удаляет поездку; чужие поездки недоступны.

# Этап 1. Агрегатор транспортных данных

Реализован мок-агрегатор, демонстрирующий точку интеграции с внешними API:

- `ApiClient` и `MockTransportApiClient` — интерфейс и мок-источник;
- `ApiRegistry` — реестр источников;
- `ApiScheduler` и `ApiTask` — периодический опрос в пуле потоков;
- `TransportUpdateMapper` — разбор JSON и преобразование в `transport_updates`;
- `AggregationService` — сохранение событий;
- `AggregatorStartup` — запуск после готовности приложения;
- `GET /api/transport/updates` — просмотр последних событий.

Настройки: `app.aggregator.enabled`, `max-tasks`, `interval-seconds`.

Мок отдаёт маршруты `39` и `7` с остановками `STOP-001`/`STOP-002`. Поэтому
статус демо-поездки на маршруте `321` остаётся `unavailable`: для `current`
нужен источник, который отдаёт `321` и остановку `67890`.

# Этап 4. Логирование, CI и frontend

## Логирование в STDOUT

- Logback пишет в консоль, формат задан в `application.yml`.
- `RequestLoggingFilter` логирует метод, путь, статус, длительность и пользователя.
- `X-Request-Id` и MDC `requestId` связывают строки одного запроса.
- Бизнес-события логируются в `TripService`, `TripStatusService` и
  `ReliabilityService`; ошибки API — в `ApiExceptionHandler`.
- Уровни меняются через `LOG_LEVEL_ROOT` и `LOG_LEVEL_APP`.

Пример строки:

```text
2026-11-21T15:14:24.737+03:00 INFO  [http-nio-8080-exec-1] [reqId=7e04...] r.s.t.service.ReliabilityService - Надёжность tripId=6 route=321 stop=67890 periodDays=30 risk=medium trips=100 avgDelay=5.00
```

## CI

GitHub Actions, файл `.github/workflows/ci.yml`:

- запуск на `push` и `pull_request` в `main`;
- JDK 21 (Temurin) и кеш Maven;
- `./mvnw -B -ntp verify`;
- отчёты Surefire сохраняются артефактом.

Тесты используют встроенный PostgreSQL, поэтому CI не требует Docker.

## Frontend

Веб-интерфейс не реализован. API поддерживает CORS и готов к вызову из
JavaScript через `fetch`.
